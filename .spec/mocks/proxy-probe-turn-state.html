探测代理池 · Turn-State 业务注入
静态 Mock，不连真实后台。核心闭环：探测轨采集 → 题目验证入池 → 住宅业务轨按轮注入。
设计预览 · 非生产页
X-Codex-Turn-State 是不透明路由状态。跨轮复用是实验行为。「答题通过」只作为入池条件，不标记为已证明的算力等级；效果以同模型同参数的启用/关闭对照测量为准。

探测轨（刷门票）

廉价动态 IPv6 探测池，独立于业务出口调度。普通连通性 ping 不采集 state。

  1. 准备海量廉价动态 IP 池图中为 IPv6。成本极低；动态供应商每次换 sid 即换出口。
  2. 发送轻量探针，不停换 IP 撞击图里的 ping 是短 Responses，不是 ICMP。目标：捕获响应头 X-Codex-Turn-State。必须仍是 gpt-6-astra，改成 Luna 则换下一个 IP。
  3. 评估过滤长度门槛（如 ≥ 160）粗筛；或/再走轻量题目（默认摸糖果题，答案 21）。筛出可用门票。
  4. 通过后入池题目答对一次即可。长度会展示，也参与筛选。

业务轨（实际生产使用）

对应原文：日常请求中强制注入 / 替换 X-Codex-Turn-State。

  1. 使用常规住宅 IP / 原 IP 组日常流量沿用账号原配置，探测池不进选路。本功能只换 state。
  2. 由网关中间件强制注入或替换 stateHTTP 写请求头；WebSocket 写请求帧 client_metadata，不看握手头。客户端自带值被覆盖。
  3. 同轮首次选票，后续钉死换账号则按新凭证重选。现有跨凭证守卫仍生效。
  4. 池空默认正常转发并后台补池可选等 2 秒，或直接 503。
JSON 导入 / 新建 Codex 账号 → 自动入队探测 → 答对一次即入池 → 业务首包注入

一句话：探测轨用廉价池刷出通过题目的 state 门票，业务轨在住宅 IP 的同轮请求里强制带上这张票。

  4. 一次真实响应的证据（任选一种）：
    • HTTP POST https://chatgpt.com/backend-api/codex/responses 的响应头，确认是否出现 x-codex-turn-state，以及它在响应头还是只在 SSE/WS 的 response.metadata.headers。
