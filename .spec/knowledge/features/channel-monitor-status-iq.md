# 渠道监控 · 状态 + 智商

在「新增渠道监控」的检查方式里增加第四项 **状态 + 智商**。用户页仍是两条时间线：上边服务器状态，下边智商状态。两码事：上游可以回复正常，但智商降了。

每轮打 **两次请求**，不能共用一条：

1. **服务器**：原来的算术探活（challenge），延迟 / 正常 / 降级 / 失败跟探活模式同一套逻辑。
2. **智商**：另发 kin 摸糖果题，只判定四态（不降智 / 降智 / 测试异常 / 监控网络异常）。

可点 Mock：`.spec/mocks/channel-monitor-status-iq.html`。

## 背景 / 目标

- 糖果题经常要十几秒。若用这一次响应同时填两条，服务器棒会被糖果题的慢延迟染成降级，看起来像通道挂了。
- 服务器通不通、快不快，跟题答得对不对，要分开看，也要分开打。
- 目标：探活归探活，智商归智商；两条棒，两枪请求。

## 题目（与 kin 默认值相同）

测试题：

> 黑色袋子中有苹果味、桃子味、西瓜味糖果;每种分为圆形和五角星形，可用手感区分形状。圆形依次有7、9、8颗;五角星形依次有7、6、4颗。事先决定摸出的数量，最少取多少颗，才能保证拿到不同形状的苹果味和桃子味糖果?

标准答案：`21`

判定：去空白和常见标点后，模糊匹配为包含标准答案；关闭模糊则为整段相等。与 `TurnStateProbeAnswerMatches` 同一套。

## 两次请求 · 两条时间线

| 请求 | 上边 · 服务器 | 下边 · 智商 |
|------|---------------|-------------|
| 算术探活成功（快） | 正常 | （本枪不改智商） |
| 算术探活成功但慢 | 降级 | （本枪不改智商） |
| 算术探活失败 / 对不上 | 失败或错误 | （本枪不改智商） |
| 糖果题答对 | （本枪不改服务器） | **不降智**（绿） |
| 糖果题完整响应但答错 | （本枪不改服务器） | **降智**（橙） |
| 糖果题接口错误、超时、空响应 | （本枪不改服务器） | **测试异常**（红） |
| 糖果题发出前监控侧 DNS 失败 | （本枪不改服务器） | **监控网络异常**（灰） |

卡片右上角标跟服务器最新态（探活结果：正常 / 降级 / 失败）。对话延迟也只取探活。智商不另做芯片，只靠下边那条棒的颜色。

没开智商的渠道，仍只有一条算术探活棒。

## 设计

- **交互面**
  - 检查方式四选一。选智商后填上游、Key、主模型，展开测试题 / 答案 / 模糊匹配。默认 kin 题和 `21`。
  - 用户状态页：开智商后两条「近 60 次」——上服务器、下智商。不展示题目原文。
- **实现面**
  - `check_mode = iq`。每个模型先发算术 challenge，再发测试题。
  - 同一轮结果写入一条历史：服务器字段来自探活，`iq_status` 来自糖果题。
  - 不抽 SVG。
  - 附加模型：每个附加模型也是两枪（探活 + 糖果题）。
  - 检测间隔仍为 15–3600 秒，抖动/启用/分组/高级设置保留。
  - 7 天可用率仍按服务器完整响应（operational + degraded）计算。
- **设计面**
  - 不并进 `/admin/channels/iq`。
  - 两条线、两枪请求。不是一条请求填两条，也不是一条线混两种意思。

## 已决策

- 题目 / 答案 / 模糊匹配：复用 kin Turn-State 探测，不用鹈鹕题。
- 展示两条时间线；探测打算术题，智商另打糖果题。
- 智商文案：不降智 / 降智 / 测试异常 / 监控网络异常。
- 附加模型：每个附加模型也打两枪。
- IQ 模式间隔下限维持 15s（与探活相同）。
- 7 天可用率按服务器完整响应（operational + degraded）计算。
