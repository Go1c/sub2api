# 用户 WebSocket 设置（已确认口径）

入口在**个人资料**；通道是 **WebSocket**；与邮件「余额不足提醒」**解耦**。

---

## 已拍板

| 项 | 结论 |
|----|------|
| WebSocket 总开关默认 | **关**（用户主动启用） |
| 余额阈值 | 与邮件**独立**存储/配置 |
| 连接范围 | **全站**（登录且总开关开后保持连接，不限资料页） |
| 站内信范围 | **全部**进收件箱的新消息都可触发（用户/管理员/系统等） |
| 卡片标题 | **WebSocket 设置** |
| 公告 | **要做**：收到/命中新公告时也可 WebSocket 通知（独立子开关） |
| 邮件默认阈值 | 系统默认 **$10**（功能 A，不并入 WS 卡） |

## 0. 两套功能，不耦合

| | **功能 A：余额不足提醒** | **功能 B：WebSocket 设置** |
|--|--------------------------|----------------------------|
| 状态 | 已有 | 新建 |
| 入口 | 个人资料现有卡片 | 个人资料**同页独立卡片** |
| 通道 | 邮件 | WebSocket |
| 本需求对 A | 仅系统默认阈值 → **$10** | 整块新建 |
| 关系 | 不依赖 B | 不依赖 A；可同时开 |

```
个人资料 /profile
├── [A] 余额不足提醒（邮件）
└── [B] WebSocket 设置
```

---

## 1. 一句话

个人资料增加 **WebSocket 设置**（默认关）。用户启用后，可分别配置：

1. 余额低于**独立阈值**时是否 WS 提醒  
2. 收到**站内信**时是否 WS 提醒  
3. 收到**公告**时是否 WS 提醒  

支持测试；全站维持连接。邮件余额提醒保持独立。

---

## 2. 功能 A（邮件 · 仅默认阈值）

- UI/逻辑保持独立，卡内**不加** WebSocket  
- 系统默认阈值：**$10**  
- 存量是否把已是 `$1` 的配置改成 `10`：实现时默认 **仅改代码/初始化默认**；若需强制刷存量另开 migration（可产品再定）  

---

## 3. 功能 B（WebSocket）

### 3.1 入口与可见性

- 个人资料 `/profile`  
- 卡片标题：**WebSocket 设置**  
- **非管理员**用户；管理员 profile 默认不展示本卡  

### 3.2 总开关

- `启用 WebSocket`，**默认关**  
- 关：不建连 / 不推送；子配置可保留但不生效  
- 开：全站登录态下建立并维持用户 WS 连接  

### 3.3 子配置（总开关打开后可配；子项默认开）

| 子项 | 含义 | 默认（总开关开后） |
|------|------|-------------------|
| 余额低于阈值时通知 | 首次跌破 **WS 独立阈值** 时推送 | 开 |
| 余额阈值 | 仅用于 WS 余额告警 | **$10** |
| 收到站内信时通知 | 收件箱新消息后额外 WS 提醒 | 开 |
| 收到公告时通知 | 用户命中/拉取到**新公告**时 WS 提醒 | 开 |

### 3.4 站内信

- 站内信本体仍在站内信模块  
- WS 只做「有新站内信」实时提醒（toast 等，可跳转 `/site-messages`）  
- 范围：**全部**写入当前用户收件箱的消息  
- `site_messages_enabled` 关：隐藏/禁用该子项，后端不推  

### 3.5 公告（新增）

**现状锚点：**

- 类型：`Announcement` / `UserAnnouncement`，`notify_mode`: `silent` | `popup`  
- 前端：`announcementStore`、`AnnouncementPopup`，登录后 `fetchAnnouncements`  

**产品语义：**

- 「收到公告时通知」= 在现有公告展示之外，当用户侧判定有**需要感知的新公告**时，用 WebSocket 推一条实时提醒  
- **不是**用公告系统替换 WS；也不是改管理员发公告的主流程为「只发 WS」  

**触发建议（实现以可验证为准）：**

- 用户已启用：WS 总开关 +「收到公告时通知」  
- 存在对该用户可见、且用户尚未以「已读/已关闭」处理完毕的新公告（与现有 announcement 已读语义对齐）  
- 推送时机优先：  
  1. **服务端**在公告发布/对用户生效时向在线用户推送（若现有模型是全局拉取，可先做「用户下次连接或服务端广播 active 公告变更」）  
  2. 与现有 `fetchAnnouncements` 互补：WS 用于即时，轮询/登录拉取仍可保留  
- `notify_mode = silent`：是否仍推 WS —— **默认仍推「有新公告」轻提示**（若产品要 silent 完全静默，实现前可再收紧为仅 `popup`）  
- 无活跃连接：本次收不到 WS；用户之后仍靠进入站点拉取公告  

**前端：** toast/条提醒，可点开现有公告弹层或公告入口。

### 3.6 测试

- 仅 WebSocket 卡内  
- 前置：总开关已开  
- 推送 `type=test`（或等价），不发邮件、不写假站内信/假公告业务数据  
- 限流（如 30s）  

### 3.7 推送条件摘要

**余额：** WS 总开 ∧ 余额子开 ∧ 阈值>0 ∧ 首次跌破 ∧ 有连接 — **不读**邮件 `balance_notify_enabled`  

**站内信：** WS 总开 ∧ 站内信子开 ∧ 站内信功能开 ∧ 新收件 ∧ 有连接  

**公告：** WS 总开 ∧ 公告子开 ∧ 新可见公告（语义对齐已读）∧ 有连接  

### 3.8 非目标

- 与功能 A UI/开关耦合  
- 用站内信/公告存储替代 WS 通道  
- 离线消息堆积补推  
- 混用 OpenAI 上游 WS / 管理端 ops WS 业务
